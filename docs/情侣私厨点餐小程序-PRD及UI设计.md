# 情侣私厨点餐小程序 PRD 及 UI 设计

版本：v1.0  
日期：2026-07-09  
产品定位：情侣 / 夫妻之间使用的私密点餐、做饭、记录小程序  
参考风格：粉色奶油系、手绘厨房贴纸、情侣小饭桌、轻量仪式感

---

## 1. 项目概述

### 1.1 产品名称

建议名称：**情侣私厨**

备选名称：

- 情侣小饭桌
- 恋爱点餐机
- 两个人的厨房
- 私厨小饭桌

### 1.2 产品一句话

情侣之间专用的点餐小程序：一个人点菜、备注口味、查看进度，另一个人管理菜单、接单、做饭、完成订单。

### 1.3 产品目标

本产品不是外卖平台，也不是普通菜单系统，而是将“今天吃什么”变成情侣之间的互动仪式。

产品需要同时满足两类目标：

1. **真实可用**：点菜、购物车、订单、菜单管理、接单、完成、评价、数据统计都要真正跑通。
2. **情绪价值**：界面要可爱、温柔、有恋爱感，让用户觉得这是“我们两个人的小厨房”。

### 1.4 核心价值

- 解决情侣之间“今天吃什么”的选择问题。
- 让做饭的一方能明确看到对方想吃什么、备注什么口味。
- 给点餐的一方提供类似餐厅点单的仪式感。
- 将每次做饭变成可记录、可评价、可回看的关系记忆。
- 通过情侣绑定，让菜单、订单、评价变成两个人专属数据。

## 2. 用户与场景

### 2.1 目标用户

主要用户：

- 情侣
- 夫妻
- 同居伴侣
- 一方经常做饭，另一方经常点菜的人
- 想把日常吃饭做成轻量互动的人

### 2.2 用户角色

| 角色 | 说明 | 核心操作 |
|---|---|---|
| 客人 | 点菜的一方 | 浏览菜单、加入购物车、备注口味、提交订单、查看进度、评价 |
| 厨师 | 做饭的一方 | 管理菜单、查看订单、接单、完成订单、查看数据 |
| 情侣成员 | 已绑定关系的用户 | 编辑资料、生成邀请、接受邀请、查看情侣关系 |

### 2.3 典型使用场景

#### 场景 A：女朋友点菜

1. 打开小程序。
2. 选择“我是客人”。
3. 进入点菜页。
4. 选择分类，例如“肉菜”。
5. 加入“可乐鸡翅 × 2”“土豆炖牛腩 × 1”。
6. 填写口味备注，例如“少辣，不要香菜”。
7. 提交订单。
8. 在“我的订单”查看厨师是否接单、是否完成。
9. 吃完后给厨师打分和评价。

#### 场景 B：男朋友做饭

1. 打开小程序。
2. 选择“我是厨师”。
3. 在厨师工作台看到待接单订单。
4. 查看菜品、数量、备注和总价。
5. 点击“接单”。
6. 做完后点击“完成订单”。
7. 等待对方评价。
8. 在店铺数据中查看评分、完成单数、最受欢迎菜品。

#### 场景 C：第一次使用

1. 用户进入首页。
2. 授权登录。
3. 编辑头像和昵称。
4. 创建或接受情侣邀请。
5. 系统初始化默认菜单。
6. 两个人开始共享同一个菜单和订单空间。

## 5. 核心业务流程

### 5.1 客人下单流程

```text
进入首页
→ 选择我是客人
→ 进入客人点菜页
→ 选择菜品分类
→ 加入菜品到购物车
→ 修改数量
→ 填写口味备注
→ 提交订单
→ 生成待接单订单
→ 进入我的订单页
→ 等待厨师接单
→ 厨师完成后提交评价
→ 订单进入历史记录
```

### 5.2 厨师处理订单流程

```text
进入首页
→ 选择我是厨师
→ 进入厨师工作台
→ 查看待接单订单
→ 点击接单
→ 订单进入制作中
→ 做完后点击完成订单
→ 订单进入已完成
→ 等待客人评价
→ 店铺数据更新
```

### 5.3 情侣绑定流程

```text
用户 A 编辑个人资料
→ 用户 A 创建情侣邀请
→ 系统生成 inviteCode 和邀请页
→ 用户 B 打开邀请页
→ 用户 B 查看邀请人资料
→ 用户 B 点击接受邀请
→ 系统校验邀请有效性
→ 创建 coupleId 或加入 coupleId
→ 双方绑定成功
→ 双方共享菜单、订单、评价、情侣空间
```

### 5.4 菜单管理流程

```text
厨师进入厨师工作台
→ 点击菜单管理
→ 查看全部菜品
→ 新增 / 编辑 / 换图 / 上下架 / 删除菜品
→ 客人点菜页同步展示已上架菜品
```

## 6. 功能需求

## 6.1 登录与用户资料

### 6.1.1 功能说明

用户首次进入小程序，需要创建个人资料。个人资料用于首页、我的页、情侣邀请、订单下单人等位置展示。

### 6.1.2 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| 头像 | 图片 | 可使用微信头像或本地上传 |
| 昵称 | 文本 | 最多 12 字 |
| UID | 文本 | 系统生成，用于展示 |
| 绑定状态 | 枚举 | 未绑定 / 已绑定 |

### 6.1.3 页面

页面标题：编辑资料  
主标题：编辑个人资料  
副标题：设置你的头像和昵称

页面元素：

- 顶部返回按钮
- 中心爱心图标
- 头像上传区域
- 昵称输入框
- 昵称字数提示，例如 `4/12`
- 保存资料按钮
- 辅助说明：头像和昵称将用于你们的情侣小饭桌

### 6.1.4 校验规则

- 昵称不能为空。
- 昵称最多 12 个字符。
- 头像为空时使用默认头像。
- 保存成功后返回上一页或我的页。

## 6.2 首页

### 6.2.1 功能说明

首页是身份入口，用户可以选择以“客人”或“厨师”身份进入。

### 6.2.2 页面内容

页面标题：情侣私厨

核心结构：

```text
顶部导航
厨房手绘装饰
主标题：情侣点餐 
副标题：今天你想以什么身份进入？
角色卡片一：我是客人
角色卡片二：我是厨师
底部厨房桌布装饰
```

### 6.2.3 角色卡片

#### 我是客人

文案：

- 标题：我是客人
- 描述：点菜、备注口味、提交订单

点击后：

- 若已登录：进入客人点菜页。
- 若未登录：引导登录。
- 若没有菜单：提示“还没有菜单，先让厨师添加菜品吧”。

#### 我是厨师

文案：

- 标题：我是厨师
- 描述：查看订单、开始制作、完成订单

点击后：

- 进入厨师工作台。

### 6.2.4 特殊状态

| 状态 | 处理 |

| 未登录 | 弹出登录授权 |

| 有进行中订单 | 客人入口可直接跳转我的订单 |

## 6.3 客人点菜

### 6.3.1 功能说明

客人可以浏览厨师维护的菜品，按分类选择菜品，加入购物车，填写口味备注并提交订单。

### 6.3.2 页面结构

页面标题：客人点菜  
主标题：今天想吃什么？  
副标题：选择分类，再挑你想吃的菜

布局：

```text
左侧：分类导航
右侧：菜品列表
中部：口味备注
底部：购物车操作栏
```

### 6.3.3 分类导航

默认分类建议：

- 肉菜
- 家常菜
- 早餐
- 汤
- 甜品
- 饮料

分类交互：

- 点击分类后右侧列表切换。
- 当前分类左侧显示粉色竖线。
- 当前分类文字使用主色粉。

### 6.3.4 菜品卡片

字段：

- 菜品图片
- 菜名
- 描述
- 价格
- 加入按钮
- 已选数量

展示示例：

```text
可乐鸡翅
甜咸口，适合下饭
¥ 28
加入
```

交互规则：

- 未加入时显示“加入”按钮。
- 加入后显示数量控制：`- 2 +`。
- 点击加号数量 +1。
- 点击减号数量 -1，减到 0 时移出购物车。
- 下架菜品不展示。

### 6.3.5 口味备注

输入框：

```text
口味备注
例如：少辣、多放葱、不吃香菜
```

建议提供快捷标签：

- 少辣
- 不辣
- 多放葱
- 少油
- 不吃香菜
- 不要蒜

点击快捷标签后自动追加到备注输入框。

### 6.3.6 底部购物车栏

展示：

```text
已选 0 份，共 ¥0
购物车
我的订单
提交订单
```

规则：

- 未选择菜品时，提交订单按钮禁用。
- 已选择菜品时，提交订单按钮高亮。
- 点击“购物车”打开购物车弹层。
- 点击“我的订单”进入我的订单页。

### 6.3.7 提交订单规则

提交前校验：

- 至少选择 1 个菜品。
- 当前用户已登录。
- 当前情侣空间存在。
- 当前没有未完成订单。
- 菜品仍处于上架状态。

失败提示：

| 场景 | 提示 |
|---|---|
| 未选菜 | 先选一道想吃的菜吧 |
| 有未完成订单 | 上一单还在制作中，先等等厨师吧 |
| 菜品已下架 | 有菜品刚刚下架啦，请重新选择 |
| 网络失败 | 订单没有送出去，再试一次吧 |

成功提示：

```text
订单已送到厨师手里啦
```

购物车用于集中查看已选菜品、调整数量、清空和提交订单。

### 6.4.2 展示方式

建议使用底部半屏弹层。

结构：

```text
购物车                    清空
```

### 6.4.3 交互规则

空状态文案：

```text
还没有选菜，去挑一道喜欢的吧
```

客人可以查看当前订单状态、取消待接单订单、查看历史订单、对已完成订单进行评价。

### 6.5.2 页面结构

页面标题：我的订单  
主标题：我的订单  
副标题：这里可以看到厨师的制作进度

页面元素：

- 查看历史订单按钮
- 当前订单卡片
- 状态说明卡片
- 评价区域

### 6.5.3 当前订单卡片

展示：

```text
当前状态：待接单

我点了这些菜
可乐鸡翅 × 2        ¥56
土豆炖牛腩 × 1      ¥38

口味备注
没有备注

合计：¥94
```

### 6.5.4 不同状态处理

| 状态 | 页面展示 | 客人操作 |
|---|---|---|
| 待接单 | 当前状态：待接单 | 取消订单 |
| 制作中 | 当前状态：制作中 | 查看进度 |
| 已完成 | 当前状态：已完成 | 提交评价 |
| 已评价 | 当前状态：已评价 | 查看评价 |
| 已取消 | 当前状态：已取消 | 查看历史 |

### 6.5.5 评价

评价区域：

```text
给厨师打个分吧
★★★★★
评价输入框
提交评价
```

规则：

- 评分范围 1-5 分。
- 默认 5 分。
- 评价文本最多 100 字。
- 每个订单只能评价一次。
- 提交评价后订单进入历史订单。

成功提示：

```text
评价已收到，厨师会偷笑的
```

## 6.6 厨师工作台

### 6.6.1 功能说明

厨师可以查看客人提交的订单，进行接单、完成、取消等操作，同时进入菜单管理、店铺数据、历史订单。

### 6.6.2 页面结构

页面标题：厨师工作台  
主标题：厨师工作台  
副标题：这里可以看到客人的点菜单

顶部功能按钮：

- 菜单管理
- 店铺数据
- 历史订单

当前订单卡片：

```text
订单状态：待接单

下单人
女朋友

点了这些菜
可乐鸡翅 × 2        ¥56
土豆炖牛腩 × 1      ¥38

口味备注
没有备注

合计：¥94

接单
取消订单
清除订单
```

### 6.6.3 订单操作规则

| 订单状态 | 主按钮 | 次按钮 | 禁用按钮 |
|---|---|---|---|
| 待接单 | 接单 | 取消订单 | 清除订单 |
| 制作中 | 完成订单 | 取消订单 | 接单 |
| 已完成 | 清除订单 | 无 | 接单、取消订单 |
| 已取消 | 清除订单 | 无 | 接单、完成订单 |

### 6.6.4 接单

点击“接单”后：

- 订单状态从 `pending` 变为 `accepted`。
- 记录 `acceptedAt`。
- 客人的“我的订单”同步显示“制作中”。

提示：

```text
已接单，准备开火啦
```

### 6.6.5 完成订单

点击“完成订单”后：

- 订单状态从 `accepted` 变为 `completed`。
- 记录 `completedAt`。
- 客人端显示评价区。

提示：

```text
这顿饭完成啦
```

### 6.6.6 取消订单

取消前需要二次确认。

确认文案：

```text
确定要取消这份订单吗？
```

取消后：

- 订单状态变为 `cancelled`。
- 客人端同步显示已取消。

## 6.7 菜单管理

### 6.7.1 功能说明

厨师可以维护专属菜单，包括新增、编辑、换图、上下架、删除菜品。

### 6.7.2 页面结构

页面标题：菜单管理  
主标题：菜单管理  
副标题：添加菜品、编辑信息、换图和上下架


```text

肉菜

¥28

下架
```

### 6.7.3 新增菜品

字段：

| 字段 | 是否必填 | 规则 |

## 7. 订单状态机

### 7.1 状态定义

| 状态值 | 中文 | 说明 |
|---|---|---|
| `pending` | 待接单 | 客人已提交，厨师未接单 |
| `accepted` | 制作中 | 厨师已接单，正在制作 |
| `completed` | 已完成 | 厨师已完成，等待评价 |
| `reviewed` | 已评价 | 客人已评价，进入历史 |
| `cancelled` | 已取消 | 客人或厨师取消 |

### 7.2 状态流转

```text
pending
├─ 厨师接单 → accepted
├─ 客人取消 → cancelled
└─ 厨师取消 → cancelled

accepted
├─ 厨师完成 → completed
└─ 厨师取消 → cancelled

completed
└─ 客人评价 → reviewed

cancelled
└─ 进入历史订单

reviewed
└─ 进入历史订单
```

### 7.3 并发规则

- 同一个情侣空间同一时间只能有一个未结束订单。
- 未结束订单包括：`pending`、`accepted`、`completed`。
- 若存在未结束订单，客人不能再次提交订单。
- 提交订单时必须重新校验菜品是否仍上架。

## 12. 是否必须使用微信云开发

结论：**不一定必须使用微信云开发。**

微信云开发只是做小程序 MVP 时最省事的一种方案，不是唯一方案。这个项目可以有三种技术路线。

### 12.1 方案 A：微信云开发

组成：

- 微信小程序前端
- 云数据库
- 云函数
- 云存储
- 微信登录 openid

优点：

- 不需要自己买服务器。
- 不需要单独搭后端服务。
- 获取用户 openid 方便。
- 云函数、数据库、存储都在微信生态内。
- 适合个人项目、小型情侣应用、快速上线。

缺点：

- 与微信生态绑定较深。
- 后续如果要做 Web、App、多端统一，迁移成本会更高。
- 复杂查询和大型后台能力不如自建后端灵活。

适合：

- 你想快速做出来。
- 主要只在微信小程序里使用。
- 用户量不大。
- 不想折腾服务器、域名、部署。

推荐程度：第一版最推荐。

### 12.2 方案 B：自建后端

组成：

- 微信小程序前端
- 自建 API 服务，例如 Node.js、Go、Java、Python
- MySQL / PostgreSQL / MongoDB
- 对象存储，例如腾讯云 COS、阿里云 OSS
- HTTPS 域名

优点：

- 技术自由度高。
- 数据完全掌握在自己系统里。
- 后续可以扩展 Web 管理后台、App、H5。
- 可以接入更复杂的权限、统计、通知、AI 推荐。

缺点：

- 需要服务器。
- 需要部署、运维、数据库备份。
- 小程序请求后端通常需要配置合法服务器域名。
- 如果正式上线，还要关注域名、HTTPS、备案、微信平台配置等事项。

适合：

- 你已经有后端基础。
- 你计划把它做成长期产品。
- 你希望未来支持多端。
- 你需要更强的数据控制能力。

推荐程度：如果你会后端，长期更稳。

### 12.3 方案 C：纯本地体验版

组成：

- 小程序前端
- 本地 storage

优点：

- 开发最快。
- 不需要服务器。
- 适合做 UI Demo 和交互原型。

缺点：

- 不能真正多人共享。
- 换手机或清缓存数据会丢。
- 情侣绑定、订单同步、厨师接单无法真实跨设备实现。

适合：

- 只想先看效果。
- 做可点击原型。
- 用来确认 UI 和流程。

推荐程度：只适合原型，不适合真实使用。

### 12.4 推荐选择

如果目标是“做一个真的可以和女朋友一起用的小程序”，建议：

第一阶段使用 **微信云开发**。

原因：

- 登录、数据库、图片存储、云函数都能快速接起来。
- 不需要先搭服务器。
- 对情侣点餐这种轻量应用非常合适。
- 第一版可以更快把核心闭环跑通。

如果后面你想做成完整产品，再考虑迁移到自建后端。

### 12.5 技术路线建议

推荐第一版：

```text
微信小程序原生开发
├─ 页面层：WXML + WXSS + JS / TS
├─ 登录：wx.login + 云开发 openid
├─ 数据库：云数据库
├─ 图片：云存储
├─ 业务逻辑：云函数
└─ 权限：基于 openid 和 coupleId 校验
```

如果自建后端：

```text
微信小程序
├─ wx.request 调用 HTTPS API
├─ 后端服务：Node.js / Go / Java
├─ 数据库：MySQL / PostgreSQL
├─ 图片：对象存储
└─ 鉴权：openid + 自定义 session/token
```

| 取消自己的待接单订单 | 下单人 |
| 厨师接单 | 情侣成员 |
| 完成订单 | 接单人或情侣成员 |
| 提交评价 | 下单人 |
| 菜单管理 | 情侣成员，第一版不区分具体厨师 |

## 15. 验收标准

### 15.1 功能验收

第一版必须满足：

- 用户可以进入小程序并创建个人资料。
- 用户可以修改头像和昵称。
- 用户可以创建情侣邀请。
- 另一用户可以接受邀请并完成绑定。
- 厨师可以新增菜品。
- 厨师可以编辑菜品。
- 厨师可以上下架菜品。
- 客人只能看到已上架菜品。
- 客人可以加入购物车。
- 客人可以修改购物车数量。
- 客人可以填写口味备注。
- 客人可以提交订单。
- 厨师可以看到待接单订单。
- 厨师可以接单。
- 客人可以看到订单变为制作中。
- 厨师可以完成订单。
- 客人可以提交评价。
- 历史订单可以查看。
- 店铺数据可以根据订单和评价更新。
- 刷新小程序后数据不丢失。

### 15.2 UI 验收

- 页面整体符合粉色奶油厨房风格。
- 首页首屏能清楚看到“我是客人”“我是厨师”两个入口。
- 所有主按钮在手机上易点击。
- 卡片内文字不溢出。
- 底部购物车栏不遮挡重要内容。
- 弹层关闭、返回、确认等交互清晰。
- 空状态和错误状态都有明确提示。

### 15.3 数据验收

- 历史订单中的菜品价格不受后续改价影响。
- 下架菜品不在客人菜单中展示。
- 删除菜品不影响历史订单。
- 同一情侣空间同一时间不能重复创建未完成订单。
- 非情侣成员不能访问该情侣空间的数据。

## 17. 风险与注意事项

### 17.1 需求风险

- 如果第一版加入太多装饰和玩法，会拖慢核心功能完成。
- 需要优先保证点菜、订单、接单、完成、评价闭环。

### 17.2 数据风险

- 订单必须保存菜品快照。
- 菜品删除不要物理删除，优先软删除。
- 关系解绑后历史订单如何处理需要明确：建议保留历史，但不再共享新订单。

### 17.3 体验风险

- 不能让页面只是好看但不能操作。
- “待添加”入口不要太多，否则会像半成品。
- 购物车、订单状态、厨师操作必须清晰。

### 17.4 上线风险

- 如果使用自建后端，需要处理 HTTPS 域名、服务器配置、接口安全等。
- 如果使用微信云开发，需要关注云资源额度、数据库权限、云函数调用成本。
- 正式上线前需要按照微信小程序平台要求完成配置和审核。

## 18. 总结

本产品第一版的关键不是做成“好看的粉色页面”，而是做成一个真正能用的情侣点餐系统。

最小成功标准：

```text
客人能点菜
厨师能接单
订单能流转
菜单能管理
评价能留下
数据能保存
两个人能共享
```

技术上不强制使用微信云开发。  
如果目标是快速做出可用版本，推荐微信云开发。  
如果目标是长期产品化，且你有后端能力，可以选择自建后端。
